# Headless WordPress Migration Report

Generated by an in-repo migration pass. Scope: replace hardcoded homepage/marketing
content with live WPGraphQL data where a matching Repository + Service already
existed, without redesigning UI, without building new backend content types.

## 1. Completed Migrations

- **Verified against production data** — `next build` statically prerendered `/`
  and `/services`, and the generated HTML contains the real live titles
  (`Digital Marketing`, `WordPress Development`, `AI Automation`,
  `SEO Optimization`, `UI/UX Design`, `Web Development TEST`), not the old mock
  copy ("CRO", "Google & Meta Ads", "Branding", etc.).

### 1.3 Fixed a live-breaking bug uncovered by turning mock mode off

Once real GraphQL calls started firing (the actual point of this migration), the
build failed with `WPGraphQL returned errors: There can be only one fragment named
"MediaFields"`. Root cause: `src/graphql/gql.ts` was a plain string-concatenation
tag with **no fragment deduplication**. `SEO_FRAGMENT` already embeds
`MEDIA_FRAGMENT` inside itself; any query file (posts, services, case studies,
portfolio) that interpolates both `${MEDIA_FRAGMENT}` directly *and*
`${SEO_FRAGMENT}` ends up with `fragment MediaFields on MediaItem { ... }` defined
twice in one document, which WPGraphQL rejects. This was invisible under mock mode
because no real request was ever sent.

Fixed at the source — `gql()` now strips duplicate `fragment Name on Type { ... }`
blocks (brace-matched, first occurrence wins) after composing the document. This is
a general fix in the one place responsible for fragment composition; it required no
changes to any individual query file and fixes the same latent bug for every
content type that shares fragments (posts, services, and any future case-study /
portfolio queries).

### 1.4 Fixed the `Service` GraphQL query to match the real live schema

The pre-existing query (`service-offering.queries.ts`), API type
(`wp-service-offering.ts`), and adapter (`service-offering.adapter.ts`) assumed
`summary`, `icon`, and `menuOrder` as top-level fields on the `Service` type. The
live schema does not expose these — a real request returned:

```
Cannot query field "summary" on type "Service".
Cannot query field "icon" on type "Service".
Cannot query field "menuOrder" on type "Service".
```

Introspection is disabled on the public endpoint, so the actual field names were
found by probing real queries against `https://tffdigital.com/graphql`. The real
shape is an ACF field group container:

```graphql
services {
  nodes {
    serviceFields {
      shortDescription   # -> domain `summary`
      description        # -> domain `content` fallback
      displayOrder        # -> domain `order`
      icon { node { sourceUrl altText mediaDetails { width height } } }
    }
  }
}
```

Updated `WPServiceFields`/`WPServiceOffering` (`src/types/api/wp-service-offering.ts`),
`GET_SERVICES`/`GET_SERVICE_BY_SLUG` (`src/graphql/queries/service-offering.queries.ts`),
and `adaptServiceOffering` (`src/adapters/service-offering.adapter.ts`) to match. Confirmed
against all 6 live entries (`digital-marketing`, `wordpress-development`,
`ai-automation`, `seo-optimization`, `ui-ux-design`, `web-development`) that the new
query returns correct data with no errors.

## 2. Reverted: `SelectedWork.tsx` (case studies)

This was migrated to `getCaseStudies()` initially, per the plan, but reverted back
to its original hardcoded array before finishing. Reason: **the `CaseStudy` and
`PortfolioItem` post types do not exist on the live WordPress GraphQL schema at
all.**

```
$ curl .../graphql -d '{"query":"query { caseStudies(first:1){ nodes{ id } } }"}'
{"errors":[{"message":"Cannot query field \"caseStudies\" on type \"RootQuery\"."}]}

$ curl .../graphql -d '{"query":"query { portfolioItems(first:1){ nodes{ id } } }"}'
{"errors":[{"message":"Cannot query field \"portfolioItems\" on type \"RootQuery\"."}]}
```

`src/repositories/case-study.repository.ts`, `src/services/case-study.service.ts`,
`src/repositories/portfolio.repository.ts`, `src/services/portfolio.service.ts`,
their adapters, and their GraphQL query files are fully implemented on the Next.js
side but call root fields that don't exist on `tffdigital.com`. Wiring
`SelectedWork` to `getCaseStudies()` would have made every homepage load throw in
production. This is not a Next.js code defect — it's a backend gap: WordPress needs
a Case Study (and/or Portfolio) custom post type registered and exposed to
WPGraphQL before this can be wired up. Left as a TODO (see §4).

## Navigation menu (partially viable, not auto-migrated)

`Navbar.tsx` and `Footer.tsx` were deliberately left hardcoded even though a
navigation repository exists, because wiring them up is materially riskier than
the content sections migrated above:

- The correct `MenuLocationEnum` value isn't known yet (see table above).
- `Navbar`'s links mix real routes with **in-page anchors** (`/#process`,
  `/#work`, `/#testimonials`) — a WP menu can technically store arbitrary URLs,
  but nothing currently maps a CMS menu item to "should scroll to this homepage
  section."
- `Footer`'s links are split into two labeled columns ("Services", "Quick Links")
  plus a separate hardcoded newsletter form, hardcoded contact details, and
  hardcoded (currently `href="#"`) social links — a single flat WP menu doesn't
  naturally produce that grouped structure without additional design/data-modeling
  decisions.

Forcing this through in the current pass would have meant guessing at a shape and
risking breaking site-wide chrome on every page, which conflicts with the
"no redesign" constraint. Recommend scoping this as its own follow-up once the
menu-location and grouping questions are answered with the WordPress team.

## Blockers for a fuller migration

1. **Case studies / portfolio**: needs WordPress-side CPT registration + WPGraphQL
   exposure before any Next.js wiring is possible.
2. **Navigation menu**: needs the correct live `MenuLocationEnum` value confirmed,
   plus a product decision on how in-page anchors and the footer's multi-column
   grouping should be represented in (or layered on top of) a WP menu.
3. **Testimonials, stats, team/founders, FAQ, industries, process steps, SEO/SMM
   page copy**: no content types exist for these yet, on either side. Each would
   need a new ACF field group or CPT, a new GraphQL query/fragment, a new
   repository/service/adapter, and a domain type — a deliberate follow-up, not
   part of this pass.
